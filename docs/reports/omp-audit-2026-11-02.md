## 2. 逐条证据

### 2.1 fork/branch 深拷贝被重复累计（高）

**本仓库代码。** OMP 的去重键是 `SessionKey + DedupKey`，即只在一个 session 内去重：

```go
// internal/data/files.go:963-971
for _, t := range f.ordered {
    key := t.SessionKey + "\x00" + t.DedupKey
    if f.a == model.Claude {
        key = t.DedupKey
    }
    if t.DedupKey != "" && seen[key] {
        continue
    }
    seen[key] = true
    ...
}
```

OMP 的 `DedupKey` 来自 `responseId`（兜底为记录 `id`），见 [files.go:893-L917](../../internal/data/files.go#L893-L917)。本仓库的设计说明也明确写了 fork 拷贝“仍然分别计数”：

> [2026-11-02-omp-agent.md:26-28](../agent-notes/implemented/feature/2026-11-02-omp-agent.md#L26-L28)  
> “Forked sessions that copy a parent prefix under a new session id still count separately — pi parity.”

**上游 OMP 行为。** `SessionManager.createBranchedSession()` 会把 root→leaf 路径上的条目**原样复制**到新文件，包括相同的 entry `id`/`timestamp`，只更换 session header id：

- `packages/coding-agent/src/session/session-manager.ts:4082-4104`：`createBranchedSession` 构造 `entriesToKeep`、生成 `newSessionId` 和新文件名。
- `packages/coding-agent/src/session/session-manager.ts:4133-4134`：`this.#entries = [...entriesToKeep, ...labels]`，条目对象本身被复用。
- `/fork` 与 `/branch` 都走 `#branchIntoNewSession`，见 `packages/coding-agent/src/session/agent-session.ts:11535-11546` 与 `:13553-13557`。

OMP 自己的统计数据库专门为这个问题做了 fork guard：按 `(entry_id, timestamp)` **跨 session_file** 去重，first-write-wins：

- `packages/stats/src/db.ts:899-914`（注释明确说 fork 会 deep-copy 相同 entry_id/timestamp/responseId，若不 guard 会“inflate every aggregate”）。
- `packages/stats/src/chunked-insert.ts:24-28`、`:47-57`（identity 冲突时跳过另一 transcript 的同一行）。

**复现结果。** 构造父文件与 fork 文件（新 session id、相同 `id=m1`/`responseId=r1`/timestamp/usage）：

```text
sessions=2 turns=2 input=200 cost=0.002
```

单次真实调用只有 `input=100`、`cost=0.001`，当前实现累计成 2 倍；`analytics.Build` 也得到 `Turns=2, Input=200`。这同时会抬高用量页的 Sessions 卡片（fork 的 SessionKey 不同）。

**触发条件。** 使用 OMP 的 `/fork`、`/tan`（fork 类命令）或会新建 session 文件的 branch 操作，且父会话已有历史用量。`model_usage` 记录同样会被拷贝，同样重复计入。

**影响。** token、费用、轮次、会话数按“父历史长度 × fork/branch 次数”线性放大。OMP 官方统计不会这样计数。**本机 `~/.omp` 只有 1 个会话文件，未出现 fork 样本；机制用合成文件确认，实际发生频率无法从本机数据判断。**

### 2.2 自定义 OMP 目录被忽略（中，条件性漏算）

**本仓库代码。** OMP 数据源写死默认路径：

```go
// internal/data/files.go:179-180
case model.Omp:
    return []string{home(".omp/agent/sessions")}
```

**上游 OMP 行为。** OMP 的路径由 `packages/utils/src/dirs.ts` 解析：

- `dirs.ts:4-11`：`PI_CONFIG_DIR` 覆盖配置根（默认 `.omp`），`PI_CODING_AGENT_DIR` 覆盖 agent 目录；Linux 上设置 XDG 变量后会迁到 `$XDG_*_HOME/omp/`。
- `dirs.ts:328-336`：默认 agent 目录是 `<configRoot>/agent`；命名 profile 是 `<configRoot>/profiles/<profile>/agent`。
- `dirs.ts:425-435`：XDG 下 `~/.omp/agent/sessions` 会变成 `$XDG_DATA_HOME/omp/sessions`（扁平，不再有 `agent/`）。
- `dirs.ts:997-1000`：`getSessionsDir(agentDir)` 返回 `<agentDir>/sessions`。

**复现结果。** 把会话放到 `PI_CODING_AGENT_DIR` 或 `PI_CONFIG_DIR` 指向的目录：

```text
PI_CODING_AGENT_DIR=<custom> -> turns=0 sessions=0
errors=[{Agent:omp Message:data source not found: <home>\.omp\agent\sessions}]
PI_CONFIG_DIR=my-omp -> turns=0 sessions=0
errors=[{Agent:omp Message:data source not found: <home>\.omp\agent\sessions}]
```

**触发条件。** 用户设置 `PI_CONFIG_DIR`、`PI_CODING_AGENT_DIR`、使用 OMP profile，或在 Linux 上启用了 XDG 迁移。

**影响。** 这些用户的 OMP 用量完全不被导入；若默认目录与自定义目录同时存在，则只统计默认目录，形成部分漏算。项目现有 Pi 导入器也是同样的写死路径，但 OMP 新增导入器时没有跟随 OMP 的目录解析规则。

### 2.3 零费用记录被冻结（中，条件性漏算）

**本仓库代码。** 任何非 adaptive 且 `RecordedCost` 非 nil（包括 0）的轮次都直接采用记录值：

```go
// internal/pricing/pricing.go:191-197
func Cost(t model.Turn, fallbackModel string) (float64, bool) {
    if !t.IsAdaptive() && t.RecordedCost != nil && valid(*t.RecordedCost) {
        return *t.RecordedCost, true
    }
    ...
}
```

OMP 解析器把 `cost.total` 的 0 也保存成指针，见 [files.go:898-L901](../../internal/data/files.go#L898-L901)；`Calculator.Cost` 同样按这条路径走（[calculator.go:23-26](../../internal/pricing/calculator.go#L23-L26)）。

**上游 OMP 行为。** OMP 的 stats 数据库把“存储的 0”当作**未知费用**，不是免费：

- `packages/stats/src/db.ts:487-517`：`storedCost.total === 0`（除 recurring tariff 外）不会直接采用，而是 `calculateCatalogCost(...) ?? storedCost ?? ZERO`。
- OMP 的 Devin provider 在流开始时把 usage/cost 初始化为 0（`packages/ai/src/providers/devin.ts:184-190`），成功结束时才调用 `calculateCost`（`:534`）。
- 错误/中断路径 `devin.ts:540-550` **没有**调用 `calculateCost`，因此失败消息可能带真实 token 但 `cost.total=0`。

**复现结果。** 构造非 adaptive OMP 消息（`devin/swe-2`，`input=1000`，`cost.total=0`）：

```text
zero recorded cost: pricing.Cost=0 ok=true
```

即本仓库把这次请求当作“已定价的 $0”，OMP 官方统计会按目录价重算。

**额外问题。** 本仓库 `resolveLocked` 只对 OMP 的 `devin/adaptive` 走 Devin Pro 定价；非 adaptive 的 `devin/swe-2` 会落到 models-dev 目录（[pricing.go:216-L224](../../internal/pricing/pricing.go#L216-L224)）。实测 `internal/pricing/models-dev-pricing.json` 没有 `swe-2` 键，因此即使不冻结 0，这类记录在本仓库也会是 unpriced/0。

**触发条件。** 非 adaptive OMP 请求出现 `usage.cost.total = 0`（失败、中断、旧版本/外部产生的部分 cost 对象），尤其是带大量 system prompt 的失败请求。

**影响。** 失败请求的 token 仍在，但费用被低估为 0。**本机唯一真实 OMP 消息的 `cost.total=0.00706425`，不是 0；零费用触发频率属于推断，未在真实历史中观察到。**

### 2.4 orchestration token 未计入（中，条件性漏算）

**本仓库代码。** OMP 解析器和聚合只读取四个对话桶：

```go
// internal/data/files.go:893-901
u := get(m, "usage")
t.InputTokens = num(get(u, "input"))
t.OutputTokens = num(get(u, "output"))
t.CacheReadTokens = num(get(u, "cacheRead"))
t.CacheCreationTokens = num(get(u, "cacheWrite"))
```

```go
// internal/analytics/analytics.go:142-145
b.Input += t.InputTokens
b.Output += t.OutputTokens
b.Cached += t.CacheReadTokens
b.CacheWrite += t.CacheCreationTokens
```

`project_json.go` 保留了整个 `usage` 对象（包括 `orchestration`），但解析器没有使用它，见 [project_json.go:43-L46](../../internal/data/project_json.go#L43-L46)。

**上游 OMP 行为。** `usage.orchestration` 是独立计费的 token 桶：

- `packages/stats/src/parser.ts:200-213`：`totalTokens` 缺失时按 `input + output + cacheRead + cacheWrite + orchestration.*` 推导。
- `packages/catalog/src/models.ts:171-185`：计价 prompt 和 cost 都显式加入 orchestration 的 input/output/cacheRead。
- `packages/coding-agent/src/session/session-loader.ts:80-88`：补全 `totalTokens` 时同样加入 orchestration。
- `packages/ai/src/providers/openai-shared.ts:4323-4330` 与 `openai-codex-responses.ts`：多 agent/编排请求会写入该字段。

**复现结果。** 构造一条带 orchestration 的 OMP 消息（主桶 10/20/30，orchestration 15/10/5，`totalTokens=90`）：

```text
imported tokens=60, OMP totalTokens includes orchestration=90
```

**触发条件。** OMP 使用会返回 `usage.orchestration` 的 provider/模型（OpenAI/Codex 风格响应、多 agent 编排、部分 xAI 多腿计费）。

**影响。** Token 卡、Token 趋势、按模型 token 分布少算；已有 `cost.total` 时费用仍正确，但若同时遇到 2.3 的缺省/零费用场景，费用估算也会少算。**本机历史没有 orchestration 样本，实际占比无法量化。**

### 2.5 使用 entry 落盘时间而非 message 请求时间（低）

**本仓库代码。** 所有 OMP 轮次的时间取自 JSONL 顶层 `timestamp`：

```go
// internal/data/files.go:706-707
at := ts(v["timestamp"])
observe(s, at)
```

`project_json.go` 没有保留 `message.timestamp`（只保留 `timestamp`、`ttft`、`duration` 等），见 [project_json.go:43-L46](../../internal/data/project_json.go#L43-L46)。

**上游 OMP 行为。** stats 解析器优先使用 assistant message 自己的 `timestamp`，只有缺失/为 0 时才回退到 entry 时间：

- `packages/stats/src/parser.ts:337-344`：`coerceEntryTimestamp(timestamp, entry)`。
- 注释明确“stored zero is the no timestamp sentinel, not 1970; fall through to the entry envelope”。

**复现结果。** 顶层 entry 时间 `2026-11-02T00:00:30Z`、`message.timestamp=1793542378000`：

```text
CreatedAt=1793577630 (entry timestamp); message.timestamp=1793542378000
```

**触发条件。** 请求跨越本地日/周/月边界，或请求开始后很久才落盘（长任务、恢复/重放）。

**影响。** 轮次被放入相邻周期，单周期总量会偏移；总历史汇总不受影响。属于低概率边界问题。

### 2.6 非 adaptive 的 `upstreamModel` 覆盖显示与缺省计价模型（低 / 待确认）

**本仓库代码。** 所有带 `upstreamModel` 的 assistant 消息都会：

1. 写入 `s.RealModel`；
2. 把 `t.Model` 改成 `provider/upstreamModel`。

```go
// internal/data/files.go:904-916
t.Model = modelName(str(get(m, "provider")), str(get(m, "model")))
...
if upstream := strings.TrimSpace(str(get(m, "upstreamModel"))); upstream != "" {
    s.RealModel = &upstream
    t.Model = modelName(str(get(m, "provider")), upstream)
}
```

**上游 OMP 行为。** `upstreamModel` 表示“实际服务的模型”，但 OMP stats 的模型归属仍使用 requested `msg.model`：

- `packages/ai/src/providers/devin.ts:269`、`:406`：`upstreamModel` 是响应路由/实际模型元数据。
- `packages/stats/src/parser.ts:251-255`、`:289`：模型列使用 `msg.model`，不使用 upstream。
- `packages/coding-agent/src/session/session-stats.ts:243-244`：upstream 只用于 routed-model 统计。

**触发条件。** 非 adaptive 请求被路由到不同模型：Devin 非 adaptive 的 `actualModelUid`、OpenRouter/Gemini 的 served model、Anthropic signed thinking 暴露的替代模型等。

**影响。** 本仓库模型分布会把费用归到 served model，而不是用户请求的模型；若该轮次没有 `cost.total`，`pricing.Cost` 会以 served model 的目录价估算，而 OMP 官方统计会以 requested model 估算。**这是提交说明中的有意设计（“每轮用自己的 upstream ID”），是否算错取决于产品口径；本审计不把它列为确定 bug。**

## 3. 已核对且未发现明显错误的点

1. **OMP 语义与字段映射基本正确。** OMP 是 Oh My Pi，记录为 pi 兼容 JSONL；`message.usage.input/output/cacheRead/cacheWrite` 与 `model_usage` 的映射和 OMP 文档 `docs/session.md:141-220` 一致。
2. **计价单位正确。** 所有价格按 per-million USD 存储，最终除以 `1e6`（[pricing.go:60-L63](../../internal/pricing/pricing.go#L60-L63)）；没有发现货币/倍率换算错误。
3. **adaptive 计费机制正确。** `Turn.IsAdaptive` 独立于显示模型；解析器对 adaptive 消息写入 `BillingModel="devin/adaptive"`；`pricing.Cost` 和 `Calculator.Cost` 都会忽略 adaptive 的 recorded estimate，走 Devin adaptive 费率；`resolveLocked` 对 OMP 的 `devin/adaptive` 走 Devin Pro 表（[model.go:93-L101](../../internal/model/model.go#L93-L101)、[files.go:908-L910](../../internal/data/files.go#L908-L910)、[pricing.go:220-L220](../../internal/pricing/pricing.go#L220-L220)）。
4. **adaptive 费率条目与 OMP 的 cache-write 规则一致。** 本仓库 `devin-pro-pricing.json` 的 `adaptive` 为 `0.5 / 2 / 0.1 / 0.5`；OMP 对 Adaptive router 的 cache write 按 input rate 计（`packages/catalog/test/devin-discovery.test.ts:985-988`），本仓库 `.5` 与 input `.5` 一致。现有 `TestAdaptiveBillingIgnoresDisplayModelAndRecordedEstimate` 通过。
5. **side-channel `model_usage` 没有丢。** `purpose` 映射到 `ContextStream`，`DedupKey` 用记录 id；失败记录只要有 `usage` 也会计数，不会因为 `errorMessage` 被过滤。
6. **聚合没有一 turn 多桶。** `analytics.Build` 命中目标桶后 `break`，窗口是半开区间 `[start,end)`，时区转换到 Unix 秒正确（[analytics.go:118-L173](../../internal/analytics/analytics.go#L118-L173)）。
7. **缓存版本已提升到 6。** 旧快照不会绕过 OMP 的 adaptive 解析修复（[data.go:122-L122](../../internal/data/data.go#L122-L122)）。
8. **子会话/advisor 记录被当作独立 session 统计**，与 OMP stats 递归扫描 session 目录的语义一致；没有发现父子重复计费（父会话的 task toolResult 里只有汇总 details，不是 assistant usage）。

2. **零费用触发频率未知。** “失败/中断请求留下 `cost.total=0`”来自 OMP `devin.ts` 错误路径的静态阅读，未在真实失败记录中观察；其他 provider 的错误路径是否也跳过 `calculateCost` 未逐一核对。
3. **adaptive 的具体数值未与线上 Devin 账户核对。** 只验证了机制和本仓库费率表；OMP 的 adaptive 价格由 Devin API 动态发现，实际账户费率/套餐折扣可能不同。
4. **orchestration 在本机用户历史中的占比未知。** 本机唯一 OMP 会话没有该字段；无法判断它是否会实际影响该用户。

这两项改动的内容是一个 OMP fork 去重修复尝试：

- `files.go`：OMP assistant 消息改为写入 `f.latest[t.DedupKey]` 并返回 `false`；`account` 对 OMP 改为使用 `latest` 并跨 session 以 `DedupKey` 全局去重。

**该修复的自带测试结果不稳定：单独运行失败，全量运行通过。** 单独运行：

```text
=== RUN   TestOmpForkCopiesDeduped
    data_test.go:193: fork copy must dedup to the parent turn:
      [{... SessionKey:omp/fork ... DedupKey:r1}]
--- FAIL: TestOmpForkCopiesDeduped
```

随后执行 `go test ./internal/data -count=1`（全量）却通过。差异来自文件 mtime：`files()` 按 mtime **降序**排列文件（[files.go:156-L163](../../internal/data/files.go#L156-L163)）；当 fork 文件 mtime 更新时它先被解析，全局 `seen` first-write-wins 先占住 `r1`，父文件反而被跳过；当两个文件 mtime 相同或父文件先到时测试通过。**去重结果取决于文件顺序而不是 lineage，这是不稳定的。** 若按 OMP stats 的 first-write-wins 语义，应先处理父文件（按 session 文件名时间或 lineage），而不是按 mtime 新到旧。

另有一个未测试的推断缺陷：`f.latest[t.DedupKey] = t` 在 `DedupKey == ""`（既无 `responseId` 也无记录 `id`）时会把同一文件里所有匿名 assistant 消息折叠成最后一条，导致漏算。OMP 正常写入有 id，但旧/外来记录可能出现空 key。

因此：**§2.1 的结论仍按审计基线 `31c912e` 成立；工作区中这个修复方向正确，但文件顺序和空 key 处理尚未完成。**
